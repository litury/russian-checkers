# Резервная копия и восстановление БД

## Результат проверки

31 октября 2026 года создана консистентная копия `checkers` и восстановлена
в отдельный локальный PostgreSQL 16. Тестовый контейнер не имел сети,
опубликованных портов и подключения к рабочему тому. После проверки удалён.
После первой проверки существующий том закреплён в Dokploy и Swarm, а
PostgreSQL штатно пересоздан на том же образе и томе. Контрольные манифесты
до и после перезапуска совпали. Копия, созданная systemd после перезапуска,
также успешно восстановлена изолированно. Рабочие данные не изменялись.

Проверены SHA-256 файла, восстановление одной транзакцией с остановкой при
ошибке, содержимое всех таблиц, определения индексов и ограничений, их валидность.
Манифест источника и дамп получены из одного экспортированного read-only снимка:
сравнение не зависит от новых записей после начала копирования.

Количество строк описывает только проверенный снимок, не текущее состояние.

## Где находится копия

На RU: `/var/backups/damka/checkers-20261031T131631567969Z.dump` и одноимённый
`.json` с контрольной суммой и манифестом. Каталог доступен только root.
Первая проверенная копия после закрепления тома и запуска systemd:
`checkers-20261031T133914726474Z.dump`. Новые копии создаются с временной меткой;
имя последней успешной находится в `/var/backups/damka/last-success.json`.
Старые локальные копии подлежат ротации, исторические имена не вечные ссылки.

Вне RU, на компьютере разработчика:
`~/Library/Application Support/russian-checkers/backups/production/`.
Там находятся дамп, манифест и `.verified.json` с результатом восстановления.
Каталог имеет права 700, файлы — 600. Это ручная внешняя копия, не настроенное
автоматическое удалённое хранилище. Права доступа не заменяют шифрование диска.

Дамп содержит данные игроков и хеши токенов. Не помещать его в Git, публичный
каталог, логи CI или сообщения. Он не содержит серверные роли, пароли PostgreSQL,
конфигурацию Dokploy и файлы приложения — их нужно сохранять отдельно.

## Повторное копирование

`tools/backupDatabase.py` запускается только на `puppetgram-ru`, находит единственный
контейнер сервиса `app-copy-redundant-panel-sv2129` и проверяет имя базы `checkers`.
Использует PostgreSQL-утилиты из самого контейнера; секреты не печатает.
Параллельные запуски блокируются. При ошибке незавершённый файл удаляется,
существующие копии не перезаписываются. Скрипт рассчитан на текущую небольшую БД:
проверка хешей читает все строки и ограничена временем выполнения.
После успешного создания хранятся 14 последних полных пар `.dump`/`.json`;
посторонние и неполные файлы не удаляются. Это 14 запусков, не обязательно 14 дней.
При свободном месте меньше 256 MiB новый запуск отклоняется.

```sh
ssh root@77.233.223.97 'systemctl start damka-db-backup.service'
```

Скачать созданные `.dump` и `.json` по SSH в закрытый каталог на другом устройстве.
Перед использованием сравнить SHA-256 дампа со значением `sha256` в манифесте.
Не удалять предыдущую проверенную копию до успешной проверки новой.

## Автоматическое расписание

На RU включён `damka-db-backup.timer`: ежедневно в 03:15 UTC с разбросом до
10 минут; пропущенный из-за выключения сервера запуск выполняется после старта.
Первый запуск через `systemctl start` проверен (`Result=success`).

Исходники unit-файлов находятся в `tools/systemd/`, установленный скрипт —
`/opt/damka-backup/backupDatabase.py`. Изменение исходников в Git само по себе
не обновляет файлы на сервере: их нужно отдельно установить и проверить.
Сервис выполняется от root для доступа к Docker socket; таймаут 240 секунд,
права новых файлов 600. Ручные и плановые запуски используют одну блокировку.

```sh
ssh root@77.233.223.97 'systemctl list-timers damka-db-backup.timer --no-pager'
ssh root@77.233.223.97 'systemctl show damka-db-backup.service -p Result -p ExecMainStatus'
ssh root@77.233.223.97 'journalctl -u damka-db-backup.service --since yesterday --no-pager'
ssh root@77.233.223.97 'cat /var/backups/damka/last-success.json'
```

Ошибка оставляет неуспешный статус systemd и запись в журнале, не обновляя
`last-success.json`. Внешние уведомления и автоматическая проверка возраста
копии пока не подключены: журнал сам по себе не является оповещением.
При отсутствии свежей успешной копии более 26 часов проверить сервис,
свободное место и доступность PostgreSQL. Ежедневная схема может потерять
изменения со времени последней копии; непрерывного архивирования WAL/PITR нет.

## Проверка восстановления

Нужен отдельный PostgreSQL 16, не рабочая база и не контейнер локальной разработки.
Пример одноразового контейнера без сети и с данными в памяти:

```sh
docker run -d --name damka-restore-check --network none \
  --memory 256m --cpus 1 \
  --tmpfs /var/lib/postgresql/data:rw,nosuid,size=128m \
  -e POSTGRES_USER=checkers -e POSTGRES_DB=checkers \
  -e POSTGRES_HOST_AUTH_METHOD=trust postgres:16-alpine
docker exec damka-restore-check pg_isready -U checkers -d checkers
```

Если такое имя уже занято — остановиться, а не переиспользовать чужой контейнер.
Дождаться готовности перед восстановлением. `trust` допустим здесь только из-за
отсутствия сети и портов; для production его не использовать. Лимиты памяти
подходят текущему снимку, при росте базы их потребуется пересмотреть.

```sh
docker exec -i damka-restore-check pg_restore \
  --exit-on-error --single-transaction --no-owner --no-acl \
  -U checkers -d checkers < /path/to/checkers-backup.dump
```

Получить контрольный манифест SQL-запросами из `table_manifest_sql()` в скрипте
резервного копирования и сравнить с полем `snapshot` исходного `.json`.
Одного успешного `pg_restore` или совпадения количества строк недостаточно.
Убедиться, что в `public` нет невалидных индексов и непроверенных ограничений.
После проверки удалить только созданный для неё контейнер:

```sh
docker rm -f -v damka-restore-check
```

Восстановление production — отдельная операция с остановкой записи, свежей
копией текущей БД, новым постоянным томом и планом переключения API. Команды
проверки выше нельзя выполнять в рабочем контейнере.

## Постоянный том PostgreSQL

У `damka-db` (`wnIRCviYAWQ-r8krOycXw`) теперь явно задан volume mount:

```text
Source: af59097ab166eec66ee7a39600972f70965922aa7e3f54c571539abe87acc39d
Target: /var/lib/postgresql/data
```

Это прежний том, закреплённый по точному имени, а не новый пустой том.
Не заменять длинное имя более красивым: Docker не переименовывает том таким
изменением, а создаёт другой. Данные не переносились.

Постоянные настройки приложения в Dokploy:

- Одна реплика, размещение `node.hostname==puppetgram-ru`.
- Обновление и откат — `stop-first`, при ошибке — `pause`, grace period 60 секунд.
- Образ закреплён на использованном digest:
  `postgres:16-alpine@sha256:cf78e76683b9ca8c5733cbbdce6c9262b45b6767934dd0a95e671f9a0fc20685`.
- Автодеплой именно БД отключён: обновления базы выполняются отдельно и вручную.
  Автодеплой клиента и API не изменён.

Обновления безопасности PostgreSQL нужно планировать отдельно с новым digest,
резервной копией и проверкой. Том local — его данные не переезжают вместе
с задачей Swarm на другую машину. Никогда не запускать две PostgreSQL-реплики
на одном каталоге данных и не очищать этот volume.

Исходные настройки сохранены в `/root/damka-db-volume-migration/` с закрытыми
правами. Это диагностический снимок, **не готовый безопасный откат**: старый
service spec не содержал явного mount. Не применять его и не запускать вслепую
`docker service rollback`. При сбое сохранить явную ссылку на текущий том,
одну реплику и `stop-first`, изучить журналы и при необходимости восстановить
копию в отдельный новый том. Не удалять исходные данные.

## Что ещё не настроено

В Dokploy нет ни одного backup destination; на RU не обнаружена конфигурация
внешнего хранилища. Поэтому ежедневные автоматические копии пока находятся
только на RU, а внешние копии на компьютере разработчика создаются вручную.
Потеря диска/сервера RU может уничтожить и базу, и её ежедневные копии.

Нужно выбрать внешнее хранилище (например, S3-совместимый bucket), предоставить
доступ через защищённые настройки, настроить шифрование, политику хранения,
уведомления об ошибках и регулярную проверку восстановления. Ключи не передавать
в переписке и не добавлять в Git. До этого система резервирования остаётся
частичной, несмотря на успешные проверки восстановления.

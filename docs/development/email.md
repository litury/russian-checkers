# Почта и восстановление профиля

Почта необязательна: гостевой профиль и игра работают без почтового провайдера.
Привязка добавляет email к существующему `player_id`, не переносит партии и не
пересчитывает рейтинг. Вход с другого устройства выдаёт новый device-токен для
того же игрока. Профили и рейтинги автоматически не объединяются.

## Настройка сервера

Три переменные задаются вместе, только на API-сервере:

- `UNISENDER_API_KEY` — новый ключ Unisender Go, не опубликованный в переписке.
- `EMAIL_FROM` — например, `noreply@auth.damka.fun`; домен подтверждён у провайдера.
- `EMAIL_SECRET` — 32 случайных байта в base64, например результат
  `openssl rand -base64 32`. Хранить как секрет, одинаковый на всех экземплярах API.

Без этих переменных `/auth/email/status` сообщает `available: false`, отправка
недоступна. Частичная настройка останавливает запуск API с ошибкой конфигурации.
Не добавлять ключи в `VITE_*`, репозиторий, клиентские сборки или логи.
Для локальной разработки переменные читает `tools/dev.mjs` из `.env.local`.
При запуске контейнера передайте их через секреты/окружение API; в Compose по
умолчанию почта выключена. Автозапуск API применяет миграцию `006_email_auth.sql`.

Ротация `EMAIL_SECRET` делает незавершённые коды и зашифрованные задания нечитаемыми:
пользователям потребуется запросить код заново. Уже привязанные адреса не теряются.

## Сценарии

1. В профиле выбрать «Привязать почту», ввести свободный адрес и код из письма.
2. На другом устройстве выбрать «Уже есть профиль», подтвердить переключение,
   ввести привязанный адрес и код. Страница перезагрузится с прежним игроком.
3. Адрес, занятый другим игроком, не привязывается. Смена почты и объединение
   профилей не реализованы. Перед переходом в другой аккаунт сохранить текущий.

Код — 6 случайных цифр, действует 10 минут от запроса. Максимум 5 проверок на
задание. Запрос ограничен по IP (20/час), игроку (5/час), адресу (5/час, 1/минуту),
подтверждение — 60/час на IP. Счётчики хранятся в PostgreSQL и переживают рестарт.
Ответ запроса одинаков для занятого/свободного и известного/неизвестного адреса.
При неверном коде счётчик фиксируется, а не откатывается вместе с транзакцией.

Email нормализуется trim + lowercase; точки и `+suffix` не удаляются. В первой
версии поддерживаются ASCII-адреса. Код привязан к запросившему гостевому профилю,
операции и случайному UUID; проверочное значение — HMAC с серверным секретом.
Успешное подтверждение атомарно расходует код, повторное использование запрещено.
Одна почта принадлежит одному игроку, у игрока не более одной почты.

## Отправка

Создание кода и задания outbox — одна транзакция. Код с адресом в outbox зашифрованы
AES-256-GCM. Обработчик получает задание через `FOR UPDATE SKIP LOCKED` и аренду
на 30 секунд. HTTP timeout — 10 секунд, до 6 попыток с увеличением задержки.
Просроченные и отменённые задания не отправляются; после завершения payload удаляется.
Задания/коды удаляются спустя сутки после истечения срока, счётчики — по истечении.
Задание, уже переданное провайдеру, отозвать нельзя; действительность кода всё равно
проверяется сервером при вводе.

Unisender получает один `idempotence_key` на задание, но его окно дедупликации —
только минута. При потере ответа возможна повторная доставка того же кода. Не
обещаем exactly-once, не генерируем новый код на каждую попытку отправки.
API success означает принятие задания провайдером, не доставку во входящие.

Шаблон содержит HTML и plaintext, без внешних картинок, tracking pixel и подмены
ссылок. Подвал отписки включён по умолчанию. Только после разрешения поддержки
Unisender задайте `EMAIL_SKIP_UNSUBSCRIBE=1`: без разрешения провайдер отклоняет
отправку с кодом 1588. Флаги обхода отписок/жалоб не
включены. У провайдера проверять доставку, в `email_outbox` — state/last_error и
provider_id; коды, токены и полный текст ответа провайдера не логировать.

## Границы безопасности

Вход по почте зависит от безопасности почтового ящика и не защищает от фишинга.
Это не MFA и не соответствие NIST AAL2. Верификация email не подтверждает личность
игрока. Device-токены пока остаются в localStorage, как в гостевом режиме; CSP/XSS
защита остаётся важной. Вход не отзывает другие устройства. Управление сессиями,
смена почты, уведомления о новых входах и passkeys — отдельные следующие этапы.

Перед production проверить новый ключ, DNS SPF/DKIM/DMARC, доступность тарифа для
внешних адресов и фактические HTML/plaintext письма. Не использовать раскрытый ключ.

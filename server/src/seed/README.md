# Изолированные demo-данные

`npm --prefix server run seed` не имеет DATABASE_URL по умолчанию и не запускает миграции. Сначала оператор готовит пустую disposable PostgreSQL существующим `server/sql/migrations/001_init.sql`. Миграционный рефакторинг не входит в этот срез.

Обязательные настройки: NODE_ENV=development, ALLOW_DEV_SEED=I_UNDERSTAND_DISPOSABLE_ONLY, DATABASE_URL с числовым loopback и явным портом без query options, SEED_DATABASE и SEED_ROLE. Имена БД и роли: `damka_seed_dev_[a-z0-9_]{1,40}`. БД принадлежит этой роли; COMMENT на БД и роли равен `damka:disposable-dev-seed:v1`. Роль без superuser/createdb/createrole/replication/bypassrls и членства в других ролях. Эти свойства проверяются SQL после подключения, перед записью. Loopback сам по себе не доказывает безопасность: создание таких обозначений разрешено только на действительно отдельной disposable БД.

SEED_ONLINE_GAMES (default 16), SEED_BOT_GAMES (default 6): канонические десятичные целые 0..100. Ноль ничего не удаляет. Уменьшение количества сохраняет ранее созданные партии; увеличение добавляет стабильные номера. Fixture damka-demo-v2 использует фиксированную базовую дату 2026-01-01 UTC, IDs и отдельный PRNG для каждого mode/index/retry. Результат зависит также от версии общих правил; изменение правил/fixture требует новой версии, иначе конфликт отклоняется.

Demo players не имеют token_hash/auth_identities и не могут войти в приложение. Это fixture статистики, не аккаунты для интерактивного тестирования. Новые guest-аккаунты для браузера создаются отдельно только на disposable API. Генератор останавливается на первом результате общих правил с историей позиций; вычислительный лимит возвращает unfinished, после ограниченных повторов весь seed отказывается от записи.

Один client, одна транзакция, advisory lock сериализует seed. Ledger `damka_dev_seed.objects` фиксирует принадлежность и fingerprint. Повторный запуск восстанавливает отсутствующие owned rows/plies, но отказывается перезаписывать изменённые/непринадлежащие fixture записи. Ошибка откатывает весь запуск. Ledger не является приложенческой миграцией. Пароли/URL/driver errors не печатаются.

Целевые unit tests: `./node_modules/.bin/vitest run server/src/seedGame.spec.ts server/src/seed/config.spec.ts`.
Реальная интеграция: с явно заданными указанными env запустить `./node_modules/.bin/vite-node server/src/seed/checks/database.ts`. Только свежая disposable БД: скрипт проверяет отсутствие public.players, самостоятельно применяет существующий SQL, проверяет rollback/repeat/concurrency/partial/collision/bot-only/zero/remediation и оставляет тестовые данные. Повтор на уже заполненной БД намеренно запрещён. Не очищать её автоматически; для повторного clean теста нужна новая согласованная БД.

## Старый публичный seed: отдельная операция отзыва

Новый seed НЕ отзывает старые предсказуемые доступы. До отдельно разрешённой операции этот риск остаётся. Нельзя отзывать по display_name, маске токена, диапазону дат или всем demo-аккаунтам. Старые имена могли принадлежать реальным игрокам.

1. Оператор по фактически развёрнутому legacy seed подтверждает максимум два точных SHA-256 токенов и связанные UUID. Сами токены не выводить в логи/команды/отчёты. Через read-only проверку сопоставить players.token_hash и auth_identities(kind=device,token_hash). Проверить историю и принадлежность, сделать согласованную резервную копию. Если происхождение не подтверждено — остановиться, не создавать manifest на основании одного имени.
2. Создать вне git защищённый JSON manifest (0600): `database`, `role`, `attestation` со значением `UUID_AND_HASH_VERIFIED_AGAINST_DEPLOYED_LEGACY_SEED`, `identities` — массив точных `{playerId,tokenHash}`. Здесь аттестация оператора является обязательным предварительным условием, а не автоматическим доказательством исторического происхождения.
3. Передать согласованный DATABASE_URL безопасным способом, без shell xtrace. По умолчанию только dry-run: `./node_modules/.bin/vite-node server/src/seed/remediation/cli.ts /absolute/private/manifest.json dry-run`. Вывод содержит только количества. При конфликте владельца хеша скрипт отказывается от операции.
4. Только после отдельного разрешения на конкретное назначение/manifest: задать `LEGACY_SEED_CONFIRM=REVOKE_CONFIRMED_LEGACY_SEED_ONLY` и вызвать тот же CLI с `apply`. До записи SQL подтверждает имя БД/роль. Транзакция и bounded table lock защищают согласованность. Скрипт обнуляет только совпадающий legacy players.token_hash и удаляет только совпадающую device identity. Остальные identities (включая email), players, matches и plies сохраняются; повтор идемпотентен. Произвольный manifest не является безопасным без шага 1.
5. Повторить dry-run (оба счётчика должны быть ноль); разрешённым read-only способом проверить сохранность игроков/истории. Старые уже аутентифицированные WS-сессии могут оставаться активными: их инвалидирование/контролируемый restart — отдельная инфраструктурная операция, не выполняемая этим скриптом. Откат путём восстановления скомпрометированных токенов небезопасен.

Самостоятельно применять remediation к живой БД запрещено. Проверка этого среза использует только синтетические UUID и случайные хеши в disposable fixture.
